# ASSISTANT INSPECTION REPORT
**Date:** September 4, 2026

## EXECUTIVE SUMMARY

The RuralPlan Assistant is **100% rule-based**, with NO LLM/API integration. Responses are generated by pattern-matching question keywords and applying hardcoded templates. This creates short, repetitive, formulaic answers that feel like a database query rather than a helpful advisor.

**Key Finding:** The assistant CAN access relevant user data, but only uses it to fill variables in pre-written sentences. There is no dynamic reasoning or contextual explanation.

---

## 1. IS IT COMPLETELY RULE-BASED?

### ✅ YES — 100% Rule-Based

**Location:** `src/lib/ruralplan/assistant.ts` — `assistantReply()` function

**Implementation:**
```typescript
// Pattern 1: Exact keyword matches
if (/(increase|increases|higher|20%|10%|what happens)/.test(q) && /demand/.test(q)) {
  // Generate response with calculated values
  return `If demand for ${product.name} increases by ${pct}%...`;
}

// Pattern 2: Multiple keyword checks
if (/(raw material|material|mango|lemon|amla|oil|salt|spice|jar|packaging)/.test(q)) {
  // Generate response
  return `To produce the recommended ${result.requiredProduction}...`;
}

// Pattern 3: Catch-all fallback
return `I can help with production planning only...`;
```

**Evidence:**
- Uses `.test(q)` regex to match keywords
- No natural language processing
- No ML/statistics
- No neural network inference
- No API calls to external AI service
- All responses hardcoded as template strings

## 4. WHERE ARE THE PREDEFINED RESPONSES?

### ✅ Found — 7 Response Templates in assistant.ts

**Pattern matching order (lines 44–120 in assistant.ts):**

| # | Pattern | Regex Test | Response Length | Template String |
|---|---------|-----------|-----------------|---|
| 1 | "I have X and demand is Y" | `nums.length >= 2 && /(have\|stock)/.test(q) && /(demand\|need\|order)/.test(q)` | ~1 sentence | Fixed formula: `With X units... you need about Y units...` |
| 2 | Demand increase | `/(increase\|higher\|what happens)/.test(q) && /demand/.test(q)` | ~1–2 sentences | "If demand increases by Xpct%, it moves from A to B units..." |
| 3 | Raw materials | `/(raw material\|jar\|packaging)/.test(q)` | ~2–3 sentences | "To produce X units... you need Y units of material..." |
| 4 | Weather/When to produce | `/(weather\|rain\|when should i produce)/.test(q)` | ~2 sentences | "Weather for district: today is..., tomorrow is..." |
| 5 | Low stock warning | `/(low stock\|minimum\|warning)/.test(q)` | ~2 sentences | "Low stock warning appears because current stock (X) is below minimum (Y)..." |
| 6 | Overproduction | `/(overproduction\|avoid over\|too much\|waste)/.test(q)` | ~2–3 sentences | "To avoid overproduction: produce against estimated demand..." |
| 7 | Why recommendation / Explain | `/(why\|explain\|report\|reason)/.test(q)` | ~2 sentences | "Recommended production is X units. Reason: demand is Y, stock is Z..." |
| 8 | Default: How much / Produce | `/(how much\|produce\|production\|plan)/.test(q)` | ~2–3 sentences | "For product: demand is X, stock is Y, produce Z units..." |
| 9 | Fallback | No match | ~2 sentences | "I can help with production planning only..." |

**Total:** 9 predefined response patterns  
**Suggested Questions:** 6 hardcoded suggestions in `SUGGESTED_QUESTIONS` array

**Problem:**
- Same question with different wording → same response
- "How much should I produce?" → same 2-3 sentence template
- "Why is my recommendation what it is?" → same template, slightly rewording
- User data changes → SAME template, just different numbers inserted
- Makes assistant feel like a form-fill rather than an advisor

## 6. DO ASSISTANT MESSAGES CAUSE UNNECESSARY API REQUESTS?

**Pattern Analysis:**

**Supabase Queries:**
- ✓ Data loaded once at app boot (in `RuralPlanProvider`)
- ✓ Data passed via context to assistant
- ✓ NO additional Supabase queries on message send
- ✓ NO duplicate data fetching

**Weather API Calls:**
```typescript
// In assistant.ts planFor() function
const weather = getWeather(ctx.district, ctx.village); // Called on EVERY message
const factor = weatherFactor(weather);
```

**Problem:**
- `getWeather()` is called for every assistant message
- Weather is likely deterministic (test data) or from cached API
- Creates unnecessary processing overhead
- NOT cached between messages

**Data Fetching on Message Send:**
1. User sends message → `assistantReply(question, ctx)` is called
2. If question matches any weather pattern:
   - Calls `planFor()` → Calls `getWeather()` → Processes weather factor
3. Unnecessary for non-weather questions
4. No memoization or caching

## 7. PERFORMANCE ISSUES — ROOT CAUSES

### ⚠️ ISSUES FOUND — Not Critical but Real

**Issue 1: Language Switching Causes Full App Re-render**
```typescript
// In app-shell.tsx
const { language, setLanguage } = useTranslation();
// When setLanguage() is called → TranslationContext value changes
// → All useTranslation() hooks re-run
// → Components re-render even if they don't use language directly
```

**Issue 2: Dashboard Recalculates Everything on Language Change**
```typescript
// In dashboard.tsx
const weather = useMemo(
  () => getWeather(settings.district, settings.village),
  [settings.district, settings.village],
); // Weather is NOT memoized based on language change
// But language is global state → triggers parent re-render
```

**Issue 3: Translation Objects Not Memoized**
```typescript
// In useTranslation.tsx
const t = (key: string, defaultValue: string = key): string => {
  const translation = getNestedTranslation(translations[language], key);
  return translation || defaultValue;
};
// getNestedTranslation() is called on EVERY t() call
// No memoization, no caching of results
// With 380+ translation keys, this adds up
```

**Issue 4: Translation JSON Always Bundled**
- All three language files (en.json 11KB, hi.json 20KB, mr.json 20KB) bundled in client
- Total: ~51KB of translation data in every user's bundle
- Used only one language at a time
- Could be lazy-loaded

**Issue 5: Language Selector in Multiple Places**
- app-shell.tsx has language selector in BOTH desktop (line ~170) AND mobile (line ~200)
- Both call `setLanguage()` on every Select change
- Potential for multiple re-renders

**Issue 6: No Memoization on AppShell Component**
- `AppShell` renders on every route change
- No React.memo wrapping
- Language context changes cause full re-render

**Severity Assessment:**
- **High:** Language switching causes visible jank/delay? (Not confirmed without profiling)
- **Medium:** Unnecessary weather recalculation in assistant
- **Low:** Translation object recreation per lookup
- **Low:** Bundled translation size (51KB is reasonable)

## PROBLEM ANALYSIS: WHY IS ASSISTANT REPETITIVE?

### Root Causes (Ranked by Impact)

1. **100% Rule-Based Design** [CRITICAL]
   - Only 9 predefined response templates
   - Pattern matching is binary (matches or doesn't)
   - No variation in explanation style
   - Same template for different question contexts

2. **No User-Specific Reasoning** [CRITICAL]
   - Uses user data only to fill template variables
   - Doesn't explain WHY numbers are what they are
   - Doesn't mention assumptions or confidence levels
   - Doesn't adapt explanation to user's skill level

3. **No Contextual Adaptation** [HIGH]
   - Doesn't track question history
   - Doesn't follow-up on previous answers
   - Doesn't remember what user already knows
   - Same response regardless of conversation flow

4. **Limited Data Utilization** [HIGH]
   - Cold Start demand estimates NOT used (available in Product.demandMode, etc.)
   - Alerts data NOT passed to assistant
   - Seasonal information NOT explicitly used
   - Weather called on every message (not cached)

5. **No Multilingual Responses** [MEDIUM]
   - All templates in English only
   - Hardcoded strings not translated
   - Users in Hindi/Marathi see English assistant

6. **No Dynamic Response Length** [MEDIUM]
   - All templates are ~1–3 sentences
   - Simple question gets same length as complex question
   - No "short answer" vs "detailed explanation" modes

## CONCLUSION

The RuralPlan Assistant is **100% rule-based** with **NO LLM integration**. It accesses rich user data but only uses it to fill template strings. Responses are short and repetitive because there are only 9 predefined templates.

The assistant CAN be dramatically improved by:
1. Making responses more contextual (explain assumptions, confidence)
2. Using more available data (Cold Start estimates, alerts, trends)
3. Adding multilingual support for responses
4. Varying response style based on question complexity
5. Optionally adding lightweight AI for more natural language

Performance issues exist but are NOT critical — mostly related to translation context propagation, not assistant logic.
